# Open questions

Implementers record here every place where the specs are ambiguous,
incomplete or contradictory, with the interpretation they chose. The spec
owner resolves each entry by changing the specs and removing it here.

| ID | Spec section | Question | Interim choice |
|----|--------------|----------|----------------|
| FFI-1 | architecture.md §5 | How do PCM samples and camera pixels cross the UniFFI boundary? `Vec<i16>` becomes a boxed `List<Short>` in Kotlin. | As byte arrays: interleaved little-endian PCM (`push_capture_i16`, `push_capture_f32`, `push_talk_capture`, `pull_playback`, `pull_talkback`), the native layout of `AudioRecord`/`AudioTrack` and `AVAudioPCMBuffer`. Camera images are tightly packed RGBA, RGB or I420 (full-range BT.601) plus a clockwise rotation; nestwatch-ffi converts and rotates to the engine's RGB/RGBA `CameraFrame`. |
| FFI-2 | architecture.md §5 | Delivery of snapshots to foreign UIs ("bounded rates"). | Foreign `StationObserver`/`ListenerObserver` callbacks on nestwatch-ffi's own tokio threads: at most one snapshot per 100 ms (latest wins), plus a 1 s heartbeat while a pairing window is open so countdowns move; events and video frames as they happen (lagging frames dropped). Snapshots carry `remaining_ms` instead of the engine's monotonic `closes_at_ms`. |
| FFI-3 | protocol.md §3.2, §3.5 | Apps that list interfaces themselves (Android) must give endpoints before the engine binds, but the port is only known after binding with fallbacks. | nestwatch-ffi probes 47100..47109 for a port free on IPv4 and IPv6, then binds exactly that port and builds invitation endpoints from the app's interface list with the core's ordering rules. A port taken between probe and bind fails the start. |
| ANDROID-1 | platforms.md §2.1, §2.2 | nestwatch-core's mDNS (`mdns-sd`) and interface listing (`if-addrs`) call `getifaddrs`, which bionic only has from API 24; the library would not load on Android 6. | nestwatch-net builds neither on Android (Advertiser/Browser report unsupported). The station advertises through `NsdManager` with the TXT data from `StationSnapshot.mdns_txt`, re-registering on change (NSD cannot update TXT). The listener browses with NSD under a `MulticastLock`, resolves one service at a time and reports results with `Listener.add_discovered` (new `ListenerEngine::add_discovered`/`remove_discovered`). Interface addresses come from `java.net.NetworkInterface`. |
| ANDROID-2 | security.md §5 | Details of "encrypted with an Android Keystore AES-GCM key". | One AES-256-GCM Keystore key (`org.nestwatch.storage.v1`, no user authentication, since a station runs unattended). Each storage value is a file `noBackupFilesDir/nestwatch/<name>.sealed` = version `1` ‖ 12-byte IV ‖ ciphertext+tag, AAD = the storage name, written with `AtomicFile`. Backups and device transfer are disabled and excluded in the manifest rules. |
| ANDROID-3 | platforms.md §2.2, security.md PRIV-4 | The camera foreground service type must be declared when the service starts (API 34 also needs the permission then), but the camera is only wanted later, possibly with the screen off; and an unattended station cannot ask for the permission when a listener first opens the view. | The station asks for the camera permission (with an explanation, optional) when the user starts the station. The service declares `microphone` plus `camera` (if granted) from the start on API 30+, plain on API 23–29. Without the permission the station reports camera availability `denied`. |
| ANDROID-4 | platforms.md §2.2 | Which foreground service type covers listener talk-back, and when does the listener service run? | The listener service (type `mediaPlayback` on API 29+) runs whenever this device has the listener role, from app start until the role is changed. Talk-back captures the microphone only while the user holds the button in the visible app, which Android allows without a `microphone` service type. |
| ANDROID-5 | product.md FR-WEB-1, protocol.md §3.3 | Must an Android station serve the browser listener? | Not in v1: the Android station serves TCP only (no HTTP/HTTPS/WebSocket and no bundled web app). Browser listeners need a desktop station. |
| ANDROID-6 | media.md §2, product.md NFR-BW-1 | Opus on Android needs libopus cross-built for every ABI. | nestwatch-ffi builds nestwatch-core without the `opus` feature on Android for now; sessions use the baseline codec. |
| ANDROID-7 | product.md FR-ST-4 | What does "dimmable to near-black" do to the backlight and screen timeout? | Dim mode switches to the `.dimmed` palette, sets the window brightness to 1 % and keeps the screen on until tapped; without dim mode the screen may turn off normally while the service keeps monitoring. |
| ANDROID-8 | product.md FR-AL-1, FR-AL-4 | Alerts when notifications are not permitted (API 33+ denial). | Sound and connection alerts then play a short tone on the alarm stream from the listener service; with permission they are high-importance notifications (channels `alert-sound`, `alert-connection`; battery on `alert-battery`, default importance). |
| RELAY-1 | rendezvous.md §3.1, §3.2 | Syntax and validation of the invitation parameter `r`, and whether `r`/`m` may appear alone. | `r` is an `http`/`https` origin (`scheme://host[:port]`, host a DNS name or IP literal, no userinfo, path, query or fragment, at most 255 bytes), normalised by lower-casing scheme and host and dropping one trailing `/`; `http` exists for self-hosted tests. `r` and `m` are valid only together; one without the other, duplicates, a malformed origin or an `m` that is not 16 bytes of base64url are errors, as for the other parameters (PROTO-10). Builders emit them after the `a` parameters. Older parsers ignore them. |
| RELAY-2 | rendezvous.md §3.2 | Storage of the mailbox identity and how "reset relay identity" is tracked. | `MailboxIdentity` = ID, secret and a generation counter (+1 per reset), stored as 53 bytes `1 ‖ generation u32 ‖ id ‖ secret` in the platform key storage (security.md §5). |
| RELAY-3 | rendezvous.md §4.1, §4.2 | Error codes beyond `mailbox-taken`, `rate-limited`, `version`, `offline`, and what clients do with them. | Additional codes: `limit` (pipe limits), `quota` (monthly budget), `session` (unknown or expired session in `accept`), `replaced` (a newer registration took over), `protocol` (malformed NWR/1), `unavailable` (server stopping or state not writable). The server closes after every `error`. Stations stop for good on `mailbox-taken` and `version`, retry at the longest backoff after `rate-limited`, `replaced` and `unavailable`, and with normal backoff otherwise. Unknown codes are kept verbatim. |
| RELAY-4 | rendezvous.md §4.2 | Candidate syntax for IPv6, size limits, unknown candidate types. | IPv6 candidates are bracketed (`udp:[2001:db8::1]:5000`); zones, port 0, unspecified and multicast addresses are invalid. At most 16 candidates of at most 300 bytes each, `observed` at most 64 bytes, `error.code` at most 64, an NWR/1 message at most 16 KiB. Receivers skip candidates they do not understand. |
| RELAY-5 | rendezvous.md §4.2 | Purpose of `connect.nonce`. | Listeners send 16 fresh random bytes per attempt; the server only checks the length. |
| RELAY-6 | rendezvous.md §4.1, §4.2 | Whose address `observed` carries in `incoming` and `accepted`, and its form behind a reverse proxy. | `registered.observed` is the station's own address; `incoming.observed` is the listener's and `accepted.observed` the station's, as the server sees them (informational). Behind a proxy only the client IP is known, so `observed` is then the bare IP without port. |
| RELAY-7 | rendezvous.md §5.2 | Probe datagram format, how probes share the socket with QUIC, and QUIC parameters. | A probe is 6 bytes `00 'N' 'W' 'R' 'P' kind` (1 = probe, 2 = answer); its first byte has the QUIC fixed bit clear, so the shared socket separates probes from QUIC packets. Every probe is answered. The listener starts QUIC towards every address a probe or answer came from (including addresses not in the candidates, as NAT mappings), first completed handshake wins. QUIC: TLS 1.3, ALPN `nwp/1`, server name `nestwatch.invalid`, a fresh self-signed P-256 certificate per attempt that the client does not verify, keep-alive 5 s, idle timeout 30 s, one bidirectional stream opened by the listener (visible to the station once the listener sends its preface). |
| RELAY-8 | rendezvous.md §4.1, §4.2 | What "drops a mailbox's registration 60 s after its control connection ends" means for `connect`s in that window, what happens when the station does not accept within 30 s, and whether `accept` is answered. | During the 60 s grace a `connect` is parked; its `incoming` is delivered when the station registers again and the session is still valid. After the grace (or for unknown mailboxes) the answer is `offline`. A session not accepted within 30 s gives the listener `offline`. A successful `accept` gets no answer (the pipe starts); an unknown or expired session gets `error session`. |
| RELAY-9 | rendezvous.md §6 | Format and lifetime of the persisted state. | One JSON file `mailboxes.json` in the state directory, keyed by `SHA-256("nestwatch-server/1 mailbox" ‖ mailbox_id)` so it holds no mailbox IDs, with the secret hash, the last registration day and the current month's byte counter. It is written atomically (temp file, fsync, rename, directory fsync, mode 0600), immediately on a first claim (before `registered`; a failed write refuses with `unavailable`) and otherwise every 30 s and on shutdown. Mailboxes unseen for 400 days are forgotten. A corrupt or unknown-format file stops the server from starting. |
| RELAY-10 | rendezvous.md §6, §8, FR-RV-5 | HTTP layout and headers of the reference server. | `/` landing page, `/app/` browser listener (extensionless unknown paths serve its `index.html`, `/app` redirects), `/downloads/`, `/healthz` (aggregate counters as JSON, `no-store`), `/nwr/1`. App CSP as NET-5 but with `connect-src 'self'` only (CSP Level 3 `'self'` covers same-host `wss:`), `Cache-Control: no-cache`; landing page and downloads get a CSP without connections, `max-age=300` and `max-age=3600`. All files get weak ETags and 304s, `nosniff`, `DENY`, `no-referrer`, COOP/CORP. Dotfiles are never served. `/nwr/1` upgrades with an `Origin` naming another host are refused (NET-4 rule). HSTS is left to the TLS-terminating proxy. |
| RELAY-11 | rendezvous.md §4.3 | Interpretation and defaults of the limits. | Pipe counts include pending sessions. "Per client IP" is the listener's address, IPv6 grouped by /64. The 2 Mbit/s rate applies per pipe and direction and delays (never drops) messages. The monthly budget (default 50 GiB per mailbox, UTC calendar month) counts both directions; when exceeded, open pipes close and new `connect`s get `quota`. Idle means no binary message in either direction (WebSocket pings do not count). Rate limits are token buckets per address: `register` 10/min, `connect` 30/min, STUN 20/s; at most 32 WebSocket connections per address; buckets are forgotten 10 minutes after they last changed. |
| RELAY-12 | rendezvous.md §4.1 | Keep-alive failure handling on the control connection. | The server drops a control connection with no frame (pings included) for 60 s; the station reconnects when nothing arrived for 50 s. A replacing registration makes the server send `error replaced` on the old connection. |
| RELAY-13 | rendezvous.md §6, §8 | Which client address the server uses behind its reverse proxy. | When the TCP peer is a loopback address (and `trust_proxy` is on, the default), `X-Real-IP`, else the last `X-Forwarded-For` entry; otherwise the TCP peer. The address is used only for limits and `observed`, never logged. |
| RELAY-14 | rendezvous.md §5.1 | Which STUN requests the server answers. | Binding requests only; responses carry XOR-MAPPED-ADDRESS (IPv4-mapped sources as IPv4) and nothing else. Unknown comprehension-required attributes get a 420 with UNKNOWN-ATTRIBUTES, except USERNAME, MESSAGE-INTEGRITY(-SHA256), CHANGE-REQUEST, PRIORITY and USE-CANDIDATE, which are ignored. Indications, responses and other methods are dropped. Clients retransmit from 500 ms, doubling, within a 3 s default budget. |
| RVAPP-1 | rendezvous.md FR-RV-1, §3.2; product.md CORE-1 | Where the station's relay setting, its mailbox and the listener's per-station relay reference are stored. | `station-settings` gains `5: relay_enabled` (default false) and `6: relay_server` (normalised origin, default `https://nestwatch.appmire.be`; missing keys decode to the defaults). The mailbox identity is stored under `relay-mailbox` as the 53-byte RELAY-2 form (its own version byte, no CBOR wrapper); it is created on the first enable, kept when the relay is turned off and replaced by "reset relay identity". Each `listener-stations` record gains `6: {0: server, 1: mailbox}` from the latest invitation with `r`/`m`; the relay is not an entry of the endpoint list. |
| RVAPP-2 | rendezvous.md §4.2, §5.1 | Which candidates each side sends, and from which socket. | Both sides bind one fresh UDP punch socket per connect/incoming (IPv4 `0.0.0.0:0`), send one STUN Binding to the server's host on port 3478 (1.5 s budget) and list the server-reflexive address first, then the socket's local interface addresses of the same family (at most 16). The station adds its invitation endpoints as `tcp:` candidates. A side that receives no `udp:` candidate (the browser sends none) skips STUN and punching. |
| RVAPP-3 | rendezvous.md §5.2 item 5 | How a relayed listener "retries punching" when the original candidates are spent. | Every 5 minutes, and at once on a network change (`ListenerEngine::network_changed`, called by apps on connectivity changes), the listener binds a new punch socket, sends a new `connect` with its candidates, closes that pipe as soon as `accepted` arrives (the station's session on it ends before the preface) and punches to the candidates it received. The first attempt starts when the relayed session is set up. On Android a network change is `ConnectivityManager` reporting a network with internet access becoming available or lost. |
| RVAPP-4 | rendezvous.md §5.2 item 4, FR-RV-3 | Exact switch-over on the listener, and what happens when the station's `replaced` (protocol.md §9) arrives before the listener's direct session is `Connected`. | When the direct session is `Connected` it takes over the station; the relayed session is closed with `replaced`; the relayed jitter buffer keeps playing until the direct one yields its first decoded frame. If the station closes the relayed session first, the listener stays live (no disconnection, no reconnect attempt) until the direct session is set up; if that fails, it reports the disconnection and reconnects normally. `listen`, `video-start` and a pending or granted talk-back request are sent again on the direct session. No reachability alert or `Connected` event fires for the switch. |
| RVAPP-5 | rendezvous.md FR-RV-5; OPEN-QUESTIONS RELAY-10 | How the browser app knows it is served by a relay server rather than by a station. | By its path: stations serve it at `/`, the relay server at `/app/` (RELAY-10). Under `/app` the app uses only the relay route through the page's own origin, for stations whose stored relay server equals that origin, and neither the page's `/nestwatch/1` nor stored station WebSockets; pairing from `<origin>/app/#<invitation>` uses the invitation's `r`/`m`. Station-served pages never use the relay (their CSP and mixed-content rules forbid it). |
| RVAPP-6 | rendezvous.md §4.2, OPEN-QUESTIONS RELAY-6; product.md CORE-3 | The relay pipe's peer is the server: which address does the station use for the pairing rate limit and the listener list? | The `observed` address from `incoming` (bare IP with port 0 when the server gives no port). A punched direct session uses the QUIC peer address. |
| RVAPP-7 | rendezvous.md FR-RV-4, media.md §5 | How "relayed video defaults to 320×240" applies to an explicit camera request. | While the path is relayed, `video-start` carries `max_w`/`max_h` capped at 320×240; after a switch to a direct path the request is sent again with the listener's own size. |
| RVAPP-8 | rendezvous.md FR-RV-1, FR-RV-4 | When station setup asks about the relay, and the wording of the path labels. | Desktop/browser UI: the first time a station runs, a sheet with the server name and the §7 "can see / cannot see" text (plus the traffic-volume note of §7) asks once ("Use the relay server" / "Not now", stored as the UI preference `relay_asked`); the setting stays off unless the user opts in. Tiles say "home network", "via VPN", "direct (internet)" or "relayed"; a direct path reached through a `tcp:` candidate is labelled by its address (VPN range, private address = home network, else direct). Station invitations also offer `<server>/app/#<invitation>` as the relay browser link. Android asks with an opt-in dialog the first time the station runs (preference `relayAsked`; dismissing it means no). |
| RVAPP-9 | rendezvous.md FR-RV-1, FR-RV-6 | Configuring headless stations. | `nestwatch station --relay <origin>` / `--no-relay` / `--reset-relay-identity` / `--no-endpoints` (relay-only invitations) / `--relay-stun-port`; desktop host and `nestwatch-station`: `NESTWATCH_RELAY=<origin>` or `off`, `NESTWATCH_RELAY_STUN_PORT`. The choice is stored like the in-app setting. `http://` origins are accepted for self-hosted tests; the default stays `https://nestwatch.appmire.be`. |
| IOS-1 | platforms.md §2.1, §2.3 | iOS 14+ needs the restricted `com.apple.developer.networking.multicast` entitlement for raw multicast sockets, so nestwatch-net's built-in mDNS (`mdns-sd`) cannot advertise or browse from an iOS app. | As on Android (ANDROID-1): the station starts with `mdns: false` and advertises `_nestwatch._tcp` through `NetService` with the TXT data of `StationSnapshot.mdns_txt` (TXT updated in place, republished on rename or a new port); the listener starts with `discovery: false`, browses with `NetServiceBrowser`, resolves and reports services with `Listener.add_discovered` / `remove_discovered`, and follows TXT changes. `NSBonjourServices` lists `_nestwatch._tcp`. Interface addresses come from `getifaddrs` in the app, so the engine never runs the Tailscale CLI probe (processes cannot be spawned on iOS). |
| IOS-2 | security.md §5, PLATFORM-3 | Keychain item details, and Keychain items surviving an uninstall (a reinstalled app would keep the old identity and trust stores). | One generic-password item per storage name: service `org.nestwatch.Nestwatch`, account = name, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (a station must start unattended after a reboot once unlocked), not synchronizable, so values are excluded from iCloud and device-to-device migration. On the first launch after an install (no `keychain-owned` marker in user defaults, which an uninstall removes) the app deletes all items of the service, so a reinstall starts with a fresh device key like the other platforms. |
| IOS-3 | platforms.md §2.3 | The audio session of the listener is unspecified (only the station's is). | Station: `playAndRecord`, mode `default`, options `defaultToSpeaker` + `allowBluetooth`, no `mixWithOthers`. Listener: `playAndRecord` (talk-back needs the microphone without switching categories mid-session) with `defaultToSpeaker`, `allowBluetooth`, `allowBluetoothA2DP` and `mixWithOthers`, so a parent's own audio keeps playing; the always-running 16 kHz playback node keeps the app alive in the background. Both rebuild their `AVAudioEngine` after interruptions, media-services resets and configuration changes. |
| IOS-4 | product.md FR-ST-4, platforms.md §2.1 | What dim mode does on iOS, where an app may set the screen brightness and the auto-lock but the brightness is a system setting. | As ANDROID-7: dim mode uses the `.dimmed` palette, sets `UIScreen.brightness` to 1 % and disables the idle timer; the previous brightness is restored when brightened and whenever the app leaves the foreground, and dimming is reapplied on return. Without dim mode the screen may lock; the station keeps listening (background audio) but its camera is unavailable until the app is in the foreground again, which the station screen says. |
| IOS-5 | product.md FR-AL-1, FR-AL-4, platforms.md §2.3 | Alerts when notifications are denied, and which alerts are time-sensitive. | Permission is asked when the listener role starts. Sound and unreachable alerts are `timeSensitive` local notifications with the default sound (entitlement `com.apple.developer.usernotifications.time-sensitive`); "reachable again" and low battery are `active`. One notification slot per station and kind (`<station id>.sound`, `.connection`, `.battery`) so a newer alert replaces the older one; banners also show while the app is open. Without permission, sound and unreachable alerts play system alert sound 1005 (with vibration) while the app runs, and the listener home shows a notice with a link to Settings. |
| IOS-6 | platforms.md §2.3, security.md PRIV-4 | When to ask for the station's camera permission: an unattended station cannot answer a prompt when a listener opens the view. | As ANDROID-3: the station asks (after its own explanation, optional) when the user starts it, right after the microphone. Denied gives camera availability `denied`; a device without a camera, or the app in the background, gives `unavailable`. The listener asks for the camera only to scan a QR code, and for the microphone at the first talk-back. |
| IOS-7 | media.md §2, product.md NFR-BW-1 | Opus on iOS needs libopus cross-built for the device and simulator slices. | As ANDROID-6: the iOS static library is built without the `opus` feature for now; sessions use the baseline codec. |
