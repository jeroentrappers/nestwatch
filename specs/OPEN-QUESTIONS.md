# Open questions

Implementers record here every place where the specs are ambiguous,
incomplete or contradictory, with the interpretation they chose. The spec
owner resolves each entry by changing the specs and removing it here.

| ID | Spec section | Question | Interim choice |
|----|--------------|----------|----------------|
| CRYPTO-1 | protocol.md §5.3 | The listener checks the station key against `device_id` "after the handshake". May it check earlier? | The listener checks as soon as the station's static key is known (after reading message 2) and aborts before writing message 3, so a station with the wrong key never receives the PSK-bound message it could guess against offline. On the wire this is identical for honest stations. |
| CRYPTO-2 | protocol.md §5.3 | Which text form of `station_device_id_ascii` goes into the code salt? | The canonical form: 16 lower-case base32 characters without hyphens (as in the `id` TXT key). |
| CRYPTO-3 | protocol.md §5.3 | Argon2id version and optional inputs are not stated. | Version 0x13 (RFC 9106), password = the 10 ASCII characters of the normalised code, no secret key, no associated data. |
| CRYPTO-5 | protocol.md §5.6 | "Close before the nonce reaches 2^32": is nonce 2^32 − 1 still usable? | Nonces 0 .. 2^32 − 1 are usable (2^32 messages per direction); encrypting or decrypting with nonce 2^32 fails with a nonce-exhausted error. |
| CRYPTO-6 | protocol.md §2.1, security.md §5 | The stored format of the device secret is not specified. | 32 raw X25519 secret bytes as generated (not pre-clamped); the public key is X25519(secret, 9), clamping applied as RFC 7748 specifies. |
| CRYPTO-7 | protocol.md §5.3 | Code normalisation: which whitespace is removed, and how is non-ASCII input upper-cased? | Only ASCII spaces and hyphens are removed; upper-casing is ASCII-only; any other character (tabs, `U`, non-ASCII) rejects the input. |
| CRYPTO-8 | protocol.md §2.2 | Should device ID parsing accept the grouped and upper-case forms? | Parsing ignores hyphens and accepts either case; the canonical (displayed in TXT) form is lower case without hyphens. |
| PROTO-1 | protocol.md §4 | No status is defined for a version-1 listener preface with an unknown mode, and the version byte of a station's `unsupported-version` reply is not stated. | `lull-proto` reports `UnknownMode`; stations should answer `unsupported-version` and close. A station always sends its own version (1) in its preface. |
| PROTO-2 | protocol.md §3.1, §6 | Maximum record size is not stated. | Derived from Noise: a transport message is at most 65535 bytes including the 16-byte tag, so a record is at most 65519 bytes and a VIDEO fragment payload at most 65501 bytes. |
| PROTO-3 | protocol.md §7.1, test-vectors.md §1 | The CBOR encoding form is not specified, yet vectors compare bytes. | Encoders use RFC 8949 §4.2.1 core deterministic encoding (definite lengths, shortest ints, shortest exact float of f16/f32, keys sorted by encoded bytes). Decoders accept any float width, indefinite-length maps/arrays and keys in any order; duplicate keys and trailing bytes are errors; non-text keys are skipped like unknown keys. |
| PROTO-4 | protocol.md §7.2–§7.12 | Which keys are required is implicit. `listen.threshold` is "used when activated"; `status` keys are "uint or null". | Every key without `?` is required, including `threshold` in continuous mode. Nullable keys (`battery`, `charging`, `talker`) must be present and may be `null`. Optional keys (`?`) treat `null` as absent and are omitted when encoding. |
| PROTO-5 | protocol.md §7, §10 | Handling of unknown text values for enumerated keys (`role`, `mode`, `camera`, `state`, `reason`). | Unknown values are a `protocol-error`, except `close.reason`, which is kept as an opaque string so a close is never rejected. |
| PROTO-6 | protocol.md §7 | Integer ranges beyond the stated ones. | Codec ids must fit u8 (they are u8 in records); `battery` is 0..=100; other uints must fit u32; a CBOR integer is not accepted where a float is specified (and vice versa); `level.dbfs` must be finite. |
| PROTO-7 | protocol.md §7.6, §7.8 | No length limit for `status.talker` and `talk-state.by`. | They are listener display names, so the 64-byte name limit applies. `app` and `close.detail` are unlimited. |
| PROTO-8 | protocol.md §6, §6.1 | Undefined AUDIO flag bits, stream values other than 0/1, empty payloads, and PING bodies of other lengths. | Undefined flag bits are sent as 0 and ignored on receipt; an unknown stream is a malformed body; an empty payload is accepted by the record layer (codecs decide); PING/PONG bodies must be exactly 8 bytes. |
| PROTO-9 | protocol.md §6.2 | Behaviour on inconsistent fragments (header fields differing within a `frame_id`, non-uniform fragment size, last fragment larger than the others, duplicate index, empty fragment) and how many incomplete frames to keep. | Inconsistent fragments are an error (the frame is discarded; the session layer may close with `protocol-error`). Up to 3 incomplete frames are kept, oldest evicted. `frame_id` is compared with RFC 1982 wrapping arithmetic; fragments of frames not newer than the last delivered one are dropped. |
| PROTO-10 | protocol.md §3.5 | Invitation parsing details: required parameters, more than 8 `a`, duplicates, case, which characters to percent-encode, and how the browser fragment is encoded. | `v`, `s`, `t` required; `n` optional (empty name); `a` beyond the eighth ignored; duplicate `v`/`s`/`t`/`n` are errors; scheme and host `invite` match case-insensitively; `n` and `a` escape everything except RFC 3986 unreserved characters (`+` is literal); the web form percent-encodes the whole invitation URI with the same set after `#`. Keys/tokens with padding or wrong length are rejected. |
| PROTO-11 | protocol.md §3.5 | Endpoint list rules beyond link-local IPv6, order inside the VPN group, and host syntax. | Loopback, unspecified, multicast and broadcast addresses are also dropped; IPv4 before IPv6 inside the VPN group as well; IPv4 link-local is kept; interface prefixes match case-insensitively; duplicates removed. DNS names are lower-cased, a trailing dot removed, `_` allowed, all-numeric last labels rejected; port 0 and IPv6 zone IDs are invalid. |
| PROTO-12 | protocol.md §3.4 | TXT parsing: whether `http`/`https` are mandatory, key case, repeated keys. | `v`, `id`, `pair` are required; `http`/`https` optional; keys case-insensitive and the first occurrence wins (RFC 6763 §6.4); `v` other than `1` is rejected. |
| SESSION-1 | protocol.md §4, §9 | Which status wins when several non-`ok` statuses apply, and whether `busy`/`rate-limited` apply to `trusted` mode. | Checked in this order: `unsupported-version` (also for an unknown mode, PROTO-1), `busy`, `rate-limited`, `pairing-closed`. `busy` applies to every mode; whether to answer `rate-limited` is the station policy's decision per mode. A preface without the `LULL` magic (or, over WebSocket, a first message that is not exactly 6 bytes) gets no answer at all. |
| SESSION-2 | protocol.md §4 | "A station MUST answer within 5 s" and "the whole handshake MUST complete within 15 s": what is measured, and does the listener have a deadline? | The station closes silently if no complete listener preface arrived 5 s after accept. Both roles close silently if setup (Noise handshake plus receipt of the peer's `hello`) is not done 15 s after the session started; including the `hello` matters because in `IKpsk2` the station's handshake completes before the listener proved the PSK. |
| SESSION-3 | protocol.md §7.2 | "Neither side sends any other record before receiving the peer's `hello`" would deadlock if read literally; what may arrive before and during setup? | Each side sends its own `hello` as soon as its handshake completes (station: right after message 2 in `IK`/`IKpsk2`, after message 3 in `XXpsk3`), then nothing else until the peer's `hello`. The first known record must be the peer's `hello` with the right `role`. The listener then requires `paired` (pairing modes only, rejected in `trusted`), `audio-config` and `status` in that order; PING/PONG are allowed after `hello`. Unknown record types and unknown control types are ignored at any time; `close` is honoured at any time; anything else is a `protocol-error`. A pairing listener is trusted only when its first record decrypts *and* is a valid `hello`. |
| SESSION-4 | protocol.md §6, §7 | Handling of valid records and messages sent in the wrong direction (for example `status` to a station, AUDIO stream 0 or VIDEO to a station, stream 1 to a listener), a second `hello`, and inconsistent VIDEO fragments (PROTO-9). | Wrong-direction messages and streams are ignored like unknown ones. A second `hello` is a `protocol-error`. An inconsistent or oversized VIDEO frame is discarded without ending the session. `audio-config` and `status` after setup are passed to the application. |
| SESSION-5 | protocol.md §8, media.md §5 | "The VIDEO queue holds at most one complete frame; a newer frame replaces a queued one": what if the queued frame is partly sent? | A frame whose first fragment was handed to the socket is finished; at most one complete frame waits behind it, and a newer frame replaces that waiting frame. Every replacement is reported for adaptation. Replacing partly sent frames would mean that on a link slower than one frame per frame interval no frame ever completes. |
| SESSION-6 | protocol.md §5.6, §7.12 | No `close` reason exists for nonce exhaustion. | The last usable sending nonce is reserved for `close` with reason `nonce-limit` (receivers keep unknown reasons, PROTO-5); a side whose receiving nonce reaches the limit also closes with `nonce-limit`. |
| SESSION-7 | protocol.md §7.9 | What counts as "sent" and "received" for keep-alive, and when keep-alive starts. | "Sent" means bytes handed to the I/O layer; "received" means any bytes from the transport. PING starts once the peer's `hello` was received and is only queued when nothing else is waiting to be sent. On the 15 s receive timeout the session sends `close` with reason `idle` (best effort) and ends. |
| SESSION-8 | protocol.md §8 | "If the CONTROL queue cannot drain for 10 seconds": drained completely, or making progress? | The session closes (without `close`, which could not be sent either) when the CONTROL queue is non-empty and no CONTROL record was taken by the socket for 10 s. The final flush of a `close` is also bounded by 10 s. |
| SESSION-9 | protocol.md §8, media.md §3 | Size of "500 ms" of AUDIO and which frame goes when full. | 25 frames of 20 ms. When full, the oldest pre-roll frame is dropped if any is queued (media.md §3 step 5), otherwise the oldest frame. |
| SESSION-10 | protocol.md §7.8 | When does a listener stop being "granted"? Who polices stream 1? | A listener stops sending stream 1 when it sends `talk-release` or receives any `talk-state` other than `granted`. The station session delivers stream 1 frames; dropping frames from a listener that is not the talker is the station engine's job. |
