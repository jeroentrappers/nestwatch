# Rendezvous and relay (NWR/1)

## 1. Purpose

Direct connections fail on many networks: carrier-grade NAT on mobile data,
guest Wi-Fi with client isolation, corporate firewalls that only allow
HTTPS, two devices both behind NAT. NWR/1 adds an **optional** server that

1. lets a listener reach a station without knowing its address
   (**rendezvous**),
2. helps both open a direct path through their NATs (**hole punching**), and
3. forwards the encrypted byte stream when no direct path exists (**relay**).

The server is never trusted with content or identity: the NWP/1 Noise
handshake (protocol.md §5) still runs end to end between the two devices,
and the server only ever sees ciphertext. Anyone can run their own server;
the project runs one at `nestwatch.appmire.be`.

## 2. Product requirements

- **FR-RV-1** A station MUST offer a setting "Reachable through a relay
  server", with the server address (default `https://nestwatch.appmire.be`)
  and a clear explanation of what the server can and cannot see (§7). The
  setting is off until the user enables it during setup or in settings.
- **FR-RV-2** When enabled, invitations carry the relay server and the
  station's mailbox (§3.2), and listeners use them whenever direct
  endpoints fail (product.md FR-NET-3 order: mDNS, stored endpoints, relay).
- **FR-RV-3** A listener connected through the relay MUST keep trying to
  establish a direct path and switch to it without interrupting audio for
  more than 500 ms.
- **FR-RV-4** Listener tiles MUST show the path: "home network", "VPN",
  "direct (internet)" or "relayed". Relayed video SHOULD default to a lower
  size (320×240) to respect relay capacity.
- **FR-RV-5** The browser listener served from the relay server's own
  origin MUST connect to stations through the relay only (browsers cannot
  open plain `ws://` to private addresses from an HTTPS page); talk-back
  works there because the origin is a secure context.
- **FR-RV-6** Users MUST be able to point stations and listeners at a
  self-hosted server.
- **FR-RV-7** A station MAY be **relay-only**: reachable through its mailbox
  and nothing else. The browser station (product.md §3.10) always is; a
  native station is when it publishes no endpoints (RVAPP-9 `--no-endpoints`).
  Its relay setting is on by definition, its invitations carry `r` and `m`
  and no `a` parameters, and it offers no direct path: its `accept` carries
  no candidates, and a listener that receives no candidates in `accepted`
  neither punches nor retries punching on that session (§5.2). The listener
  tile shows the path "relayed" for as long as the session lasts.

## 3. Identifiers

### 3.1 Server address

An HTTPS origin, e.g. `https://nestwatch.appmire.be`. The rendezvous
WebSocket is `wss://<host>/nwr/1`; the address-discovery service is UDP
port 3478 on the same host name (§5.1).

### 3.2 Mailbox

- `mailbox_id`: 16 random bytes generated by the station when the user
  enables the relay. Shown in invitations as `m=<base64url>`.
- `mailbox_secret`: 32 random bytes kept by the station; the server stores
  only `SHA-256(mailbox_secret)` on first registration (trust on first use)
  and requires the secret for later registrations of that mailbox, so nobody
  who learns the mailbox ID from an invitation can take it over.
- Invitations add `r=<percent-encoded server origin>` and `m=<mailbox_id>`.
  Trusted listeners store both per station. A station that disables and
  re-enables the relay keeps its mailbox; "reset relay identity" creates a
  new one (and requires re-sharing).

## 4. Rendezvous protocol

All rendezvous messages are CBOR maps (as protocol.md §7.1) in binary
WebSocket messages on `wss://<host>/nwr/1`.

### 4.1 Station registration

The station keeps one **control connection** open while active:

```
station → server  { t: "register", v: 1, mailbox: bstr16, secret: bstr32 }
server  → station { t: "registered", observed: tstr }   // station's public IP:port as seen
server  → station { t: "error", code: tstr }            // "mailbox-taken", "rate-limited", "version"
```

Keep-alive: WebSocket ping every 20 s; the server drops a mailbox's
registration 60 s after its control connection ends. A new registration with
the right secret replaces an existing one.

### 4.2 Listener connect

```
listener → server { t: "connect", v: 1, mailbox: bstr16, nonce: bstr16, candidates: [tstr] }
server   → station (control) { t: "incoming", session: bstr16, candidates: [tstr], observed: tstr }
station  → server (new connection) { t: "accept", session: bstr16, candidates: [tstr] }
server   → listener { t: "accepted", candidates: [tstr], observed: tstr }
```

- `session` is chosen by the server (16 random bytes) and is valid for
  30 s.
- After `accepted`, both WebSockets become a **relay pipe**: every
  subsequent binary message from one side is forwarded unchanged to the
  other. NWP/1 runs over this pipe exactly as over a direct WebSocket
  (protocol.md §3.3): the listener sends its preface, the Noise handshake
  follows, and the relay can read none of it.
- `candidates` are each side's direct endpoints for hole punching (§5):
  `udp:<ip>:<port>` (local addresses and the server-reflexive address from
  §5.1) and optionally `tcp:<host>:<port>` (the station's NWP/1 TCP
  endpoints).
- If the mailbox is not registered the server answers
  `{ t: "error", code: "offline" }`; the listener retries with backoff.

### 4.3 Limits

The server MUST enforce, and SHOULD make configurable:

- at most 16 concurrent relay pipes per mailbox and 4 per client IP;
- a relay rate of 2 Mbit/s per pipe (audio needs < 0.1 Mbit/s; video adapts,
  media.md §5) and a monthly transfer budget per mailbox;
- idle timeout 60 s, pipe lifetime 24 h (sessions reconnect);
- connection-rate limits per IP for `connect` and `register`.

## 5. Hole punching

### 5.1 Address discovery

The server answers STUN Binding Requests (RFC 8489, the binding method only,
no authentication) on UDP 3478. Each side sends one from the UDP socket it
will use for the direct path and adds the returned XOR-MAPPED-ADDRESS to its
candidates as `udp:` (server-reflexive), alongside its local interface
addresses.

### 5.2 Punching and the direct transport

1. Both sides send small UDP probes from that socket to every `udp:`
   candidate of the peer, every 100 ms for up to 5 s.
2. The direct transport is **QUIC** (RFC 9000) on that socket, one
   bidirectional stream carrying the NWP/1 byte stream exactly as TCP does
   (protocol.md §3.1 framing). The station is the QUIC server. QUIC's own TLS
   uses a throw-away self-signed certificate that the client does not verify:
   authentication is the NWP/1 Noise handshake inside, which binds the
   session to the devices' static keys.
3. The listener starts a QUIC connection to each candidate pair that sees a
   probe come back; the first that completes wins.
4. The listener then runs a fresh NWP/1 session (mode `trusted`) over the
   QUIC stream. Once it is `Connected`, the listener closes the relayed
   session with close reason `replaced` (protocol.md §7.12, §9), so the
   station switches without delay. Audio continuity: the listener keeps
   playing the relayed stream until the first direct frame is decoded.
5. If no direct path forms, the session stays relayed; the listener retries
   punching after network changes or every 5 minutes, unless the station's
   `accepted` carried no candidates at all (a relay-only station, FR-RV-7):
   then the session simply stays relayed.

TCP candidates (`tcp:`) are tried as ordinary NWP/1 TCP endpoints; they
succeed when the station has a reachable public port (for example a port
forward or IPv6 without a firewall).

## 6. Server behaviour

- Serves, over HTTPS behind the host's reverse proxy: the landing page, the
  browser app (built from `apps/web`; listener, and relay-only station of
  product.md §3.10), the download page, and the `/nwr/1` WebSocket endpoint.
  The app's pages allow the microphone and the camera for the page's own
  origin (the browser station needs both).
- Keeps all state in memory except the mailbox secret hashes and transfer
  counters (persisted, so a restart does not let a mailbox be taken over).
- Logs aggregate counters only (registrations, pipes, bytes, errors). It
  MUST NOT log mailbox IDs, IP addresses beyond what abuse protection needs
  for at most 24 h, or message contents.

## 7. Privacy and security

What the server operator can learn: that a station is online, its public IP
address, which IP addresses connect to its mailbox and when, and how many
bytes flow. What it cannot learn: audio, video, control messages, device
names, pairing codes or keys, because everything after the preface is Noise
ciphertext between the two devices, and invitations (with the mailbox ID)
never pass through the server.

Threats and mitigations:

| Threat | Mitigation |
|--------|------------|
| Malicious or compromised server injects or alters traffic | Noise authentication fails; the session closes. |
| Server impersonates a station | Needs the station's static key (IK/IKpsk2); impossible. |
| Someone with an invitation hijacks the mailbox | Registration needs the mailbox secret (TOFU hash). |
| Denial of service by flooding a mailbox | Per-IP and per-mailbox limits (§4.3); stations keep working on LAN/VPN paths. |
| Traffic analysis (when the baby cries, from byte counts) | Sound activation reveals activity by traffic volume; listeners may choose continuous mode for relayed sessions. Documented to users. |

## 8. Deployment profile

The reference server is a single static binary (`nestwatch-server`) that
listens on a local HTTP port behind the host's reverse proxy (TLS
termination, WebSocket upgrade for `/nwr/1`) and directly on UDP 3478. It
needs no database; state lives in one directory. A self-hosting guide
(`docs/self-hosting.md`) shows the reverse-proxy configuration for nginx and
Caddy, the firewall ports (TCP 443, UDP 3478), and a systemd unit.
